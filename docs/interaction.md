# devctl 交互流程提案

状态：规划，尚未实现。本文补充工作区、项目、服务三层控制，并将早期方案的“默认级联停止”调整为“默认仅停止选中范围”。

## 1. 三层操作模型

用户可以独立启动/停止一个项目，也可以统一启动/停止一套 workspace。所有操作最终作用于服务进程。

```text
reader workspace
├─ infra project          /srv/dev/infra
│  └─ db service          postgres
├─ api project            /srv/dev/reader-api
│  ├─ api service         cargo run
│  └─ worker service      cargo run --bin worker
└─ web project            /srv/dev/reader-web
   └─ web service         pnpm dev
```

一个项目可以有多个服务。项目目录本身没有启动命令；“启动 api 项目”就是启动其默认服务组合及这些服务必需的依赖。一个项目只有一个服务时，操作体验等同于启停这个服务。

| 选中范围 | 启动 | 停止 | 重启 |
| --- | --- | --- | --- |
| 服务 | 目标及必要依赖 | 目标，取消等待/重试 | 目标；若尚未请求运行则提示使用启动 |
| 项目 | 该项目 autostart 服务及必要依赖 | 项目内全部托管服务，取消等待/重试 | 项目内当前期望运行的服务 |
| 工作区 | 全部 autostart 服务及必要依赖 | 当前工作区全部托管服务，取消等待/重试 | 当前期望运行的服务集合 |

批量操作是一次集合请求：先计算计划，再按依赖调度；不是 UI 逐个模拟按键。工作区重启先逆依赖停止，再按就绪条件启动；项目重启的停止范围只包含该项目，启动时检查并补齐必要依赖。

`autostart` 决定项目/工作区的默认启动组合，不控制进入管理界面时是否自动执行；显式启动单服务始终可以选中它。项目没有默认服务时，显示“没有默认启动服务，请展开选择”，不偷偷启动全部可选服务。只含目录而没有服务的项目显示“未配置服务”。

项目启动后不自动启动依赖它的其他项目。例如启动 API 不启动前端；启动前端可能启动 API 和数据库。

## 2. 进入与离开工作区

P0 有三种入口，命令均为拟定接口：

```text
devctl --config /path/to/devctl.toml tui
    加载、校验，进入界面，不启动服务

devctl --config /path/to/devctl.toml run
    启动工作区默认组合，进入界面

devctl resume
    恢复最近工作区的期望服务组合，进入界面
```

正常流程：选定配置 → 查看项目与服务 → 启动需要的范围 → 查看就绪进度与日志 → 按需启停 → 结束会话。P1 提供工作区别名、列表和切换入口；P0 切换时先结束当前前台会话，再进入另一份配置。

P0 的 `q` 是“结束会话”：停止全部托管服务，保存退出前期望运行的组合，恢复终端。工作区“停止全部”是用户主动清空运行组合，保持界面打开；之后退出不会恢复旧的运行组合。

P1 引入后台后，才区分“离开界面、保留运行”和“停止工作区”；管理入口可以 attach 已存活的 supervisor。

## 3. 主界面

```text
Workspace: reader                     Ready 3 · Stopped 1
┌─ 项目与服务 ─────────────────┬─ 日志 / 详情 ────────────────────┐
│ reader                       │ 10:03:01 [db] ready              │
│   infra                      │ 10:03:02 [api] listening :8080   │
│     db       就绪            │ 10:03:03 [web] ready             │
│   api                        │                                  │
│     api      就绪            │ 当前范围：web 项目               │
│     worker   已停止          │ 默认服务：web                    │
│ > web                        │ 依赖：api → db                   │
│     web      就绪            │                                  │
└──────────────────────────────┴──────────────────────────────────┘
s 启动范围 · x 停止范围 · r 重启范围 · / 搜索 · ? 操作菜单
```

左侧选中 workspace 行时，操作覆盖工作区；选中项目行时聚合该项目；展开后可选单服务。右侧默认显示选中范围的聚合日志，切换到详情查看命令、目录、依赖和错误。顶部数量按服务统计。

项目行显示就绪/运行/停止/失败数量；workspace 和项目不会仅因“某个服务存在 PID”就显示全部就绪。无 readiness 的服务显示“运行，未配置就绪检查”。

启动、停止按钮附近始终显示范围。启动范围跨出当前项目时，计划显示额外依赖；普通操作直接执行，并持续显示进度，不为每次操作重复弹确认。

## 4. 依赖如何影响独立操作

假设 DB → API → web，其中箭头表示启动顺序：

| 操作 | 预期结果 |
| --- | --- |
| 启动 web 项目 | 缺少的 DB/API 自动启动；先等 DB 就绪，再 API，再 web |
| 启动 API 项目 | 启动 API 默认服务及依赖，不启动 web |
| 停止 web 项目 | web 停止；API/DB 保留运行 |
| 重启 API 服务 | API 旧实例清理后重新启动；web 保留运行，暂时显示依赖降级 |
| 停止 API 项目 | API 项目服务停止；web 保留运行但显示依赖降级；DB 保留 |
| 级联停止 API 项目 | 停止 web 等传递下游，再停止 API 项目；DB 保留 |
| 停止 workspace | web → API → DB，独立分支可并行停止 |

“独立启动”表示操作范围可单独选择；必要依赖仍按配置满足，不提供跳过依赖的默认捷径。只希望启动前端并连接外部 API 的场景，应在配置中明确为无需托管 API 的运行方式；P1 可通过 profile 选择。

“独立停止”表示不会自动停止范围外项目。停止依赖后，其他进程是否能继续提供功能取决于它们自身的重连与容错；UI 准确显示依赖不可用。

当停止目标有范围外下游时，详情与操作菜单显示：

```text
目标：API 项目
范围内：api、worker
依赖影响：web 将失去 API，仍保持运行

停止选中范围        默认操作 x
级联停止           范围预览：web → api、worker
```

级联停止涉及等待和退避中的下游，也要撤销它们的运行意图，不能只停止已存在的 PID。范围内停止顺序遵循依赖，不盲目按服务列表顺序。

用户停止的依赖不会因已运行下游仍被期望运行而自动拉起；下游已配置的崩溃重试也只能等待依赖。只有新的显式启动、重启或恢复请求才可重新请求该依赖运行。用户重新启动 API 后，仍期望运行的等待下游可继续，已被明确停止的下游不会自行启动。

## 5. 状态反馈与失败流程

启动过程显示“等待 db 就绪 → 启动中 → 等待 API 就绪 → 就绪”；停止过程显示“停止中 → 已停止”。失败展示发生阶段、退出原因、重试次数和下一次重试时间。

依赖最终失败时，下游展示完整原因，例如“web 未启动：API 被 DB 就绪超时阻塞”。无关项目继续运行。批量启动不承诺事务式全部成功，不因一个失败就回滚所有已启动服务。

重复启动已运行目标不创建第二实例；停止已停止目标是幂等操作；重复重启在进行中显示操作已受理，不叠加多轮重启。

项目或工作区重启使用当前期望组合，保留用户手动关闭的服务。首次尚未运行任何服务时，“重启”提示使用“启动”；重试最终失败且仍期望运行的服务可以通过重启重新尝试。

## 6. CLI 与 TUI 一致性

P0 CLI 可选择启动范围，运行后进入 TUI 或 no-tui：

```text
devctl run                     # workspace 默认组合
devctl run --project api       # API 项目默认组合及依赖
devctl run api                 # service ID 为 api 的单服务及依赖
devctl plan --project api      # 查看项目启动计划，不执行
```

`--project` 与位置参数服务列表互斥，避免项目 ID 和服务 ID 同名时歧义。路径参数继续统一使用 `--config`。`run --no-tui` 不提供键盘控制，Ctrl-C 结束整个前台会话。

P0 独立停止和重启在当前 TUI 内完成；第二个终端不会创建另一个 supervisor 来控制已有实例。P1 有 IPC 后，再提供如下独立控制命令：

```text
devctl start --project api
devctl stop --project api
devctl stop --project api --cascade
devctl restart api
devctl stop                    # 停止当前 workspace
```

这些命令复用同一引擎规则，不设计 CLI 与 TUI 两套停止策略。所有示例都是规划接口，仓库目前尚未实现。
