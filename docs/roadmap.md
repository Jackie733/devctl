# 实施路线

主线：三个项目的统一终端管理。范围以 [requirements.md](requirements.md) 为准，每个当前小步记录在 [tasks.md](tasks.md)。2026-10-10 已根据真实场景收缩原规划，原里程碑的范围和后续承诺不再适用。

## 1. 首版阶段

| 阶段 | 交付物 | 完成标准 | 需求 |
| --- | --- | --- | --- |
| M1 配置 | 项目目录、命令、路径解析与校验 | 三个项目可表达；从任意目录校验；无效配置不启动进程 | W01–W03 |
| M2 单项生命周期 | 启动、信号停止、进程组清理与退出报告 | 派生后代被清理；忽略 TERM 时超时强杀；退出可解释 | P01、P02、P04 |
| M3 多项目管理 | 并发运行、单项与全部控制、运行锁 | 三项同时运行；单项停止互不影响；退出时全部清理 | P01、P07、P04、R02 |
| M4 终端界面与日志 | 项目列表、状态、按项目查看日志、操作键 | 能完成选择与启停；近期日志有界；退出恢复终端 | U01、L01、L03 |
| M5 真实项目试用 | web、小程序、中台完整流程 | 用户完成需求文档中的首版使用验收，核实平台与残留情况 | X01、首版全部需求 |

## 2. 推进规则

- 每步必须关联上述需求，并说明它改善哪个已确认场景；必要的进程和日志安全边界也要关联到对应验收。
- 已有配置与计划代码继续保留，不把已有代码等同于整个阶段已验收。
- 当前先完成 M2 的在途改动审查；需要时补齐 M1 的实际缺口，再进入 M3。
- M3 可用简短文本反馈验收控制行为，M4 接入已验证的进程管理；不把 TUI 降为可选的首版外功能。
- 产品行为或首版范围变化先与用户核对；局部 Rust 实现由助手按最小可维护方案推进。
- 用户试用后再决定新功能，不预排依赖编排、恢复、后台等未经确认的后续阶段。

## 3. 按需学习

M2/M3 学习 Child 所有权、异步等待、信号和任务回收；M4 再学习终端事件、界面状态与渲染分离。每步只解释当前代码涉及的 Rust 概念，不要求提前引入完整引擎接口或阅读所有参考项目。
