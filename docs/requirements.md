# devctl 产品需求

本文是产品范围与验收依据；操作细节见 [interaction.md](interaction.md)，实现机制见 [DESIGN.md](../DESIGN.md)，当前任务见 [tasks.md](tasks.md)。

## 1. 已确认的使用场景

2026-10-10，用户确认日常同时开发三个独立目录中的项目：

| 项目 | 开发命令 |
| --- | --- |
| web 端 | `pnpm run dev` |
| 微信小程序端 | `npm run dev:weapp` |
| Node.js 中台 | `npm run dev` |

当前痛点是逐个打开项目终端、执行启动命令，停止时又要切换终端。目标是在一个终端界面中集中管理：能同时启动全部项目，也能选择单个项目启停并查看日志；结束开发时全部停止。

三个命令可以同时启动，不需要 devctl 等待中台就绪。首版以这个实际场景验收，不以通用服务编排能力作为目标。

## 2. 首版范围与验收

沿用已有需求编号；拆小后的验收只覆盖下表范围，历史版本中更大的规划不再作为首版承诺。

| 编号 | 首版能力 | 可观察的验收结果 |
| --- | --- | --- |
| W01 | 配置多个项目目录与命令 | 一份配置包含上述三个项目，无需切换目录逐个运行 |
| W02 | 路径解析 | 相对路径基于配置文件目录；绝对路径、空格路径可用；调用目录不影响结果 |
| W03 | 启动前校验 | 无效目录、空命令、未知字段或项目引用在启动前报错，校验不执行命令 |
| P01 | 单项目启动与停止 | 启停所选项目不影响其他项目；重复启动不会创建第二实例 |
| P07 | 全部启动与停止 | 三个命令均被启动，不等待任一命令结束或业务就绪；停止全部覆盖正在启动的实例 |
| P02 | 失败反馈 | 标明哪个项目启动失败或意外退出，显示原因、退出码或信号；其他项目保留运行 |
| P04 | 可靠退出 | 单项停止、停止全部、退出界面均清理所属进程组并回收直接子进程；超时强杀 |
| L01 | 查看项目日志 | 可查看选中项目的 stdout/stderr，来源明确；界面能保留近期输出供查看 |
| L03 | 有界日志 | 大量输出、超长行或坏编码不造成无限内存增长；截断和丢弃有提示 |
| U01 | 终端管理界面 | 显示三个项目的状态，支持选择、单项启停、全部启停、查看日志和退出 |

为了可靠完成上述体验，首版同时遵守以下工程约束：

- R02：同一配置只允许一个管理实例；误开第二个 devctl 时明确报错。
- X01：先验证当前 Linux 环境；用户实际运行环境还需确认，不从当前开发环境推断 Windows 或 WSL2 已获支持。
- 信号退出与界面退出使用同一清理路径；发生可处理的错误时也清理进程并恢复终端。
- 只管理本次创建的进程，不接管或终止其他终端启动的程序。主动脱离进程组的 daemon 不属于首版清理保证。
- 日志缓冲、单条记录及队列必须有上限；具体初始预算属于设计参数，不把容量数字当成用户需求。

## 3. 首版使用验收

1. 配置三个真实项目，进入终端界面，一次启动全部；三个原有开发命令都在正确目录下运行。
2. 切换项目查看输出，能够判断启动情况；进程存活不等于业务就绪，不显示未经检测的“就绪”。
3. 停止 web 项目，中台和小程序保持运行；再次启动 web，只产生一个新实例。
4. 某个命令不存在、端口冲突或程序退出，界面指出项目及原因，其他项目可继续使用；不自动重启失败项目。
5. 退出界面后，三个项目及其托管后代全部停止；再次启动不会因为本轮残留进程而占用端口。

先用受控测试程序验证进程清理和失败行为，再由用户在真实项目上完成以上流程。测试通过不能代替用户确认操作体验。

## 4. 暂不纳入与待确认

依赖编排与就绪探针（D01–D03）、自动重启（P03）、会话恢复（R01）、后台运行（P05）、日志搜索与持久化（L02、L04）、profiles、PTY 和跨平台扩展均不进入当前主线。单项目重启快捷键也暂不必需，可先停止再启动。这些是候选能力，不是已经承诺的下一阶段。

保留已有配置与计划代码，不为范围收缩进行破坏性删除；新的运行流程不得悄悄忽略已有依赖配置。遇到首版不支持的执行配置，启动前明确拒绝。

仍需实际试用确认：三个项目的路径、运行平台，以及开发命令是否需要 stdin 交互。微信开发者工具、编辑器、依赖安装和项目自身构建配置由用户照常管理；当前只托管给出的三个命令。
